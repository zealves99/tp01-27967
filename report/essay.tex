	\section{Introdução e Glossário Técnico}
	
	O presente relatório técnico descreve o fluxo de trabalho de \textbf{Extração, Transformação e Carregamento (ETL)} implementado no \textbf{Pentaho Data Integration (PDI)} (Kettle). O objetivo principal é calcular e analisar o consumo de energia ao longo de um espetáculo de teatro, a partir de dados programados numa mesa de controlo de iluminação.
	
	\subsection{Contexto Técnico de Iluminação}
	
	Este projeto utiliza conceitos fundamentais da programação de luz para teatro:
	
	\begin{itemize}
		\item \textbf{grandMA2:} É um sistema de controlo de iluminação profissional (mesa de luz). Permite ao designer programar e guardar o estado da luz no espetáculo.
		\item \textbf{Cue (Deixa):} É um estado de luz guardado. Uma \textit{Sequence} é uma lista ordenada de \textit{Cues} que define o espetáculo. O sistema de ETL calcula o consumo de energia durante o tempo de duração de cada \textit{Cue}.
	\end{itemize}
	
	\subsubsection{Equipamentos de Iluminação}
	Os projetores são classificados em duas categorias principais, essenciais para o cálculo do consumo:
	\begin{itemize}
		\item \textbf{Dimmers / Projetores Convencionais:} Equipamentos de luz simples (e.g., lâmpadas de halogéneo) cuja intensidade é controlada diretamente através de um \textbf{dimmer} (variador de intensidade). São controlados por um único valor de intensidade ($\text{0}\%$ a $\text{100}\%$) e têm uma potência fixa.
		\item \textbf{Fixtures (Projetores Inteligentes):} Equipamentos de luz modernos (e.g., \textit{Moving Light}s ou \textit{LEDs}). Estes são controlados por múltiplos parâmetros (cor, posição, zoom, etc) e têm um consumo de potência que pode variar consoante a função ativa. Nesta primeira fase do projeto, vamos considerar apenas o consumo do atributo de \textit{dimmer}, ou seja, a intensidade da luz.
	\end{itemize}
	
	\subsection{Dados de Origem e Fluxo de Processamento}
	
	O Kettle recebe dois tipos de ficheiros exportados da grandMA2:
	\begin{itemize}
		\item \textbf{Cue Data (XML):} Contém a intensidade de controlo (valor DMX, $\text{0}$ a $\text{255}$) para cada aparelho de luz (todos os seus atributos) em cada \textit{Cue}, juntamente com os tempos de transição.
	\item \textbf{Patch Data (CSV):} Ficheiros de \textit{patch} exportados da grandMA2 que contêm a informação de mapeamento de cada aparelho: ID (Fixture/Channel), \textit{FixtureType}, nome e a que \textit{Layer} (camada de iluminação) pertence. \textbf{Não contêm dados de potência.}
	\item \textbf{Power Consumption Data (\texttt{power\_consumption.csv}):} Ficheiro criado externamente que contém a informação da \textbf{Potência Máxima} em Watts associada a cada \textit{FixtureType} ou \textit{Channel ID} (para Dimmers), permitindo realizar o cálculo de consumo.
	\end{itemize}
	
	O fluxo de ETL processa esta informação em cadeia:
	\begin{enumerate}
		\item Combina \textit{Cue Data} com \textit{Patch Data} e \textit{Max Power}.
		\item Calcula a Potência Instantânea ($P_{\text{inst}}$) e a Energia ($\text{Wh}$) consumida em cada momento do espetáculo.
		\item Os resultados são usados para gerar gráficos (via Python/Node-RED) e distribuídos por e-mail.
	\end{enumerate}

	\subsection{1. \texttt{Get\_CueData\_From\_XML.ktr} (Extração ds Dados exportados pela grandMA2)}
	Esta transformação é responsável por extrair os níveis de intensidade (DIM) e os tempos de cada \textit{cue} a partir do ficheiro XML exportado da grandMA2 (\texttt{marat-sade.xml}). Nesta fase, ainda desprezamos os tempos de \textit{fade} de cada \textit{cue}, assumindo que os valores são o máximo ao longo de toda a cue.
	
	\begin{itemize}
		\item \textbf{Passo Chave:} \textit{Get data from XML}.
		\item \textbf{Lógica:} A transformação itera sobre os elementos XML que contêm a informação dos canais/fixtures por \textit{cue}.
		\item \textbf{Extração de Tempo:} Para simular o tempo entre \textit{cues}, o passo \textit{Modified JavaScript value} gera um valor aleatório (entre $\text{10}$ e $\text{420}$ segundos), que é associado a cada \textit{CueNumber} e usado para calcular a energia.
	\end{itemize}
	
	O snippet do JavaScript para simular o tempo entre \textit{cues} é:
\noindent
\begin{KettleCode}
// Gera um valor aleatório (em segundos) para simular o tempo entre Cues.
var betweenCuesTime = Math.floor(Math.random() * (420 - 10 + 1)) + 10;
\end{KettleCode}

	\subsection{3. \texttt{Calculate\_Power\_Consumption.ktr} (Cálculo de Consumo)}
	Esta é a transformação de cálculo central.
	
	\begin{itemize}
		\item \textbf{Entrada:} Recebe o \textit{CueData} (intensidade DMX e tempo entre \textit{cues}) e os dados de Patch/Potência (\textit{MaxPower}, \textit{Layer}) gerados na transformação anterior.
		\item \textbf{Passo Chave:} \textit{Stream Lookup} e \textit{Modified JavaScript value}.
		\item \textbf{Lógica de Lookup:} Associa o \textit{MaxPower} e o \textit{Layer} a cada linha de \textit{CueData} (Stream Lookup, usando \textit{FixtureID} ou \textit{ChannelID}).
		\item \textbf{Lógica de Cálculo:} O passo \textit{Modified JavaScript value} executa o cálculo de Potência e Energia:
	\end{itemize}
	
	Snippet do JavaScript para cálculo de Potência e Energia:
	\noindent
\begin{KettleCode}
// Normaliza a intensidade: converte valor DMX (0-255) para percentagem (0-1)
var val = parseFloat(Value);
if (val > 1) val = val / 255;  

// Calcula o Consumo Instantâneo de Potência (Potência em Watts)
// P = Intensidade Normalizada * Potência Máxima
var P = val * parseFloat(MaxPower);

// Calcula a Energia (Dur é o tempo entre cues, em segundos)
var dur = parseFloat(betweenCuesTime);
var E_J = P * dur; // Energia em Joules
var E_Wh = E_J / 3600; // Energia em Watt-hora (Wh)

// Arredonda para duas casas decimais e define os campos de saída
PowerUsed = Math.round(P * 100) / 100;
Energy_J  = Math.round(E_J * 100) / 100;
Energy_Wh = Math.round(E_Wh * 100) / 100;
\end{KettleCode}
	\begin{itemize}
		\item \textbf{Saída:} Cria os ficheiros \texttt{fixture\_consumption.csv} e \texttt{dimmer\_consumption.csv}.
	\end{itemize}

	\section{Fluxo de Visualização Node-RED}

	\begin{itemize}
		\item \textbf{Caminho Base:} O caminho absoluto atual é \texttt{H:\textbackslash LESI\textbackslash ISI\textbackslash tp01-27967\textbackslash data\textbackslash output\textbackslash}.
		\item \textbf{Caminho a Substituir:} O utilizador deve substituir a porção do caminho que aponta para a pasta do projeto (\texttt{H:\textbackslash LESI\textbackslash ISI\textbackslash tp01-27967}) pelo caminho local onde o projeto está guardado.
	\end{itemize}
	
	Os nós que requerem esta atualização são os nós \texttt{inject} (\texttt{\textbf{Read Fixture CSV}} e \texttt{\textbf{Read Dimmer CSV}}) e os nós \texttt{file} de saída (\textit{\textbf{Layer Graph Data out}}, \textit{\textbf{Fixture Graph Data out}}, \textit{\textbf{Total Power Graph Data out}} e \textit{\textbf{Total Energy Graph Data out}}). Por exemplo, o caminho:
	\begin{KettleCode}
		H:\LESI\ISI\tp01-27967\data\output\fixture_consumption.csv
	\end{KettleCode}
	deve ter a parte \texttt{H:\textbackslash LESI\textbackslash ISI\textbackslash tp01-27967} substituída pelo \textit{path} local do novo utilizador.
	
	\subsection{Visão Geral do Fluxo Node-RED}
	
	O fluxo Node-RED desempenha as seguintes tarefas principais:
	\begin{enumerate}
		\item \textbf{Leitura e Injeção:} Utiliza nós \texttt{inject} para carregar manualmente os ficheiros \texttt{fixture\_consumption.csv} e \texttt{dimmer\_consumption.csv}.
		\item \textbf{Parsing e Conversão:} Os dados CSV lidos são convertidos em \textbf{arrays} de objetos JavaScript (nós \texttt{function}).
		\item \textbf{Junção e Achatamento (Flatten):} Os dados de \textbf{Fixtures} e \textbf{Dimmers} são unidos (nó \texttt{join}) e convertidos numa lista única (nó \texttt{Flatten Arrays}).
		\item \textbf{Agregação e Transformação de Gráficos:} Os dados são agregados por \textit{Layer} e \textit{FixtureType}, e formatados para diferentes tipos de gráficos (Barras, Circular) e Tabelas.
		\item \textbf{Cálculo Total:} É calculada a \textit{Total Power Usage} e \textit{Total Energy Usage} para apresentar em indicadores (\textit{gauges}).
		\item \textbf{Visualização e Saída de Dados:} Os dados são apresentados no \textbf{dashboard} (nós \texttt{ui\_chart}, \texttt{ui\_table}, \texttt{ui\_gauge}) e, em paralelo, os dados agregados para os gráficos são exportados como JSON (nós \texttt{file}) para uso futuro pelo \textit{script Python} (e.g., \texttt{layer-graph-data.json}).
		\item \textbf{Orquestração HTTP:} O fluxo inclui um nó \texttt{http in} (\texttt{/trigger}) para ser acionado remotamente pelo Kettle, iniciando o pipeline de processamento e visualização no Node-RED.
	\end{enumerate}
	
	\subsection{Esquema de Agregação de Dados (Node-RED)}
	Os nós \texttt{function} para agregação (e.g., \texttt{Aggregate Power by Layer}) são cruciais, pois transformam o fluxo de dados plano (por \textit{Cue}/aparelho) numa estrutura sumarizada que é adequada para gráficos.
	
	Snippet do JavaScript para \texttt{Aggregate Power by Layer}:
	\noindent
\begin{KettleCode}
let data = {};
msg.payload.forEach(row => {
	let layer = row.Layer || 'Unknown';
	// Soma o PowerUsed de todas as linhas por camada
	data[layer] = (data[layer] || 0) + parseFloat(row.PowerUsed || 0);
});
		
msg.payload = [{
	series: ["PowerUsed"],
	data: [ Object.values(data) ],
	labels: Object.keys(data)
}];
		
return msg;
\end{KettleCode}

	\section{Conclusão e Trabalhos Futuros}
	
	O projeto demonstrou com sucesso a aplicação de um pipeline de ETL utilizando o Pentaho Data Integration para processar dados heterogéneos (XML, CSV) provenientes de um sistema de controlo de iluminação profissional (grandMA2). O fluxo de trabalho alcançou o objetivo de calcular o consumo de energia instantâneo e total por aparelho e por camada (Layer) de iluminação, culminando na geração automatizada de relatórios visuais (Python/Node-RED) e na distribuição por e-mail.
	
	\subsection{Limitações e Melhorias Futuras}
	
	A principal limitação atual reside na precisão temporal do cálculo de consumo e na dependência de caminhos de ficheiros fixos:
	\begin{itemize}
		\item \textbf{Tempo de Cue Simulada:} O tempo de duração entre \textit{cues} é atualmente um valor aleatório (simulado), o que torna o cálculo da energia ($\text{Wh}$) aproximado.
		\item \textbf{Falta de Portabilidade:} A necessidade de codificar caminhos absolutos (no Kettle e Node-RED) compromete a portabilidade "plug-and-play" do projeto.
	\end{itemize}
	
	Para endereçar estas limitações, o principal trabalho futuro sugerido é:
	\begin{itemize}
		\item \textbf{Implementação de Logger em LUA/Python na grandMA2:} Desenvolver um \textbf{plugin} ou \textbf{macro} dentro da consola grandMA2 que corra em tempo real durante o espetáculo. Este \textit{plugin} faria um \textit{log} do \textit{timestamp} da mesa (utilizando o relógio interno da grandMA2) cada vez que é dado um "Go" (mudança de \textit{cue}). A exportação deste \textit{log} permitiria ao Kettle utilizar os \textbf{tempos de transição reais}, substituindo o valor aleatório simulado e garantindo a máxima precisão no cálculo de consumo energético total.
	\end{itemize}
